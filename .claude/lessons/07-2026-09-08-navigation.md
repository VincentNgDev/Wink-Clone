# Lesson: Navigation — where it stands today, and how it generally works

## Current state: real navigation exists, via a plain `Intent`

**Update (2026-09-09):** when this lesson was first written, `LandingActivity` was the
app's only screen and its "Get started" button did nothing. That's no longer true — the
home screen shipped (`.claude/changes/2026-09-09-add-home-screen.md`) and
`LandingActivity.onGetStartedClick` now actually navigates. See
[[09-2026-09-09-home-screen-feature-and-lists]] section 1 for the full walkthrough of the
real code; the short version:

```kotlin
// LandingActivity.kt
onGetStartedClick = {
    startActivity(Intent(this, HomeActivity::class.java))
    finish()
}
```

`AndroidManifest.xml` (see [[02-2026-09-08-android-manifest]]) now declares two screens:

```xml
<activity android:name=".ui.landing.LandingActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>
<activity android:name=".ui.home.HomeActivity" android:exported="false" />
```

`LandingActivity` (`ui/landing/LandingActivity.kt`) is still the entry point (see
[[01-2026-09-08-app-entry-point]]) — it just isn't the *only* screen anymore.
`HomeActivity` has no `<intent-filter>` and `exported="false"`, so unlike
`LandingActivity` it can only ever be reached from inside this app, via that explicit
`Intent`, never launched directly by the OS.

The rest of this lesson — the two navigation *models* and when to reach for each — was
written before that code existed and is still accurate as general Android knowledge; it's
kept below for that reference value, now with a concrete example to point back to instead
of a hypothetical one.

## The two Android navigation models (both worth knowing)

### 1. Activity-to-Activity, via `Intent` (the classic/manual approach)

Each screen is its own `Activity` subclass (like `LandingActivity`), each declared in the
manifest. To go from one to another, you build an `Intent` describing "start this
Activity class" and call `startActivity(...)`:

```kotlin
// LandingActivity.kt — real code in this project (see the "Current state" section above)
onGetStartedClick = {
    startActivity(Intent(this, HomeActivity::class.java))
    finish()
}
```

- The OS pushes the new Activity onto a **back stack**; pressing the system Back button
  pops it and returns to the previous Activity (whose `onStop()`→`onRestart()`→
  `onStart()`→`onResume()` lifecycle runs again — see [[03-2026-09-08-android-lifecycle]]).
- Each Activity gets its own layout XML, and typically its own ViewModel — e.g. an
  `OnboardingActivity` would pair with an `OnboardingViewModel` under
  `viewmodel/onboarding/`, mirroring `ui/`'s subpackage per `.claude/rules/folder-structure.md`.
- `Intent` can also carry data between screens (`putExtra("key", value)` /
  `intent.getStringExtra("key")`), and can target *other apps'* components too (e.g.
  opening a URL) — that dual purpose ("navigate within my app" and "ask the OS/another
  app to do something") is why it's called `Intent` rather than just "navigation".

### 2. The Jetpack **Navigation Component** (the modern, recommended approach for multi-screen flows within one Activity)

Instead of one Activity per screen, a single Activity hosts a `NavHostFragment`, and each
"screen" is a `Fragment`. A `nav_graph.xml` resource declares every destination and the
possible transitions between them, and you navigate with:

```kotlin
// hypothetical
findNavController().navigate(R.id.action_landing_to_onboarding)
```

- Handles the back stack, argument-passing (type-safe with Safe Args), and
  transition animations for you, driven by the declarative graph instead of manual
  `Intent` wiring.
- Generally preferred for an app whose screens are all "inside" one flow (like signing up,
  browsing, chatting) — reserving separate Activities for genuinely separate entry
  points (e.g. deep links from outside the app, or truly independent app sections).
- Not set up in this project yet — no `androidx.navigation` dependency in
  `gradle/libs.versions.toml`/`app/build.gradle.kts`, and no `nav_graph.xml` exists.

## What this means for adding the next screen

This project now has two Activities linked by one `Intent` hop, still with no Navigation
Component dependency — so the lowest-friction path for a *third* screen (say, the
Search or Profile bottom-nav tabs `HomeActivity` currently leaves as no-ops, per
[[09-2026-09-09-home-screen-feature-and-lists]]) is the same `Intent`-based approach:
add a new Activity + ViewModel under matching `ui/<feature>/`, `viewmodel/<feature>/`
subpackages (per `.claude/rules/folder-structure.md`), declare it in the manifest, and
wire the relevant click handler to `startActivity(...)`. If the app grows into several
more *interconnected* screens after that — especially ones the user bounces between
rather than moving through once, forward-only, the way Landing → Home does — switching to
the Navigation Component (Fragments under one Activity) becomes worth the added setup.
That's still a call to make once there's a real multi-screen flow to justify it, not
before.

## Key takeaway

"Navigation" in Android isn't a single built-in router the way it might be in a web
framework — it's either manual (`Intent` + `startActivity`, one Activity per screen) or a
separate library (Navigation Component, Fragments inside one Activity). This project
uses the manual model today, for the one real hop it has (Landing → Home); the Navigation
Component remains a "when it's actually worth it" upgrade, not a "should have used it from
the start" gap.
